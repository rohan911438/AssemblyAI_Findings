=== Secondary finding: validation-ordering bug (sample_rate) ===
The 120000ms duration guard uses the client-supplied sample_rate BEFORE that
rate is validated against the allowlist [8000,16000,22050,24000,32000,44100,48000].
Result: an invalid sample_rate yields a MISLEADING 413 instead of the correct 415,
depending purely on how the bogus rate skews the duration math.

  sr=1, n=100   implied 100000ms (<120000)  -> 415 "unsupported sample rate 1"   (correct)
  sr=1, n=1000  implied 1000000ms (>120000) -> 413 "audio exceeds 120000 ms"      (WRONG/misleading)
  sr=2, n=16000                              -> 413 "audio exceeds 120000 ms"      (WRONG/misleading)
  sr=7999, n=32000 implied ~4000ms           -> 415 "unsupported sample rate 7999" (correct)

=== Secondary finding: llm_instruction length limit not enforced ===
Docs: llm_instruction max 2048 chars. Observed: accepts >=20000 chars with HTTP 200.
Only a generic "config part too large" (400) triggers near ~100KB.
Sibling fields ARE strictly enforced:
  stt_prompt > 6000 chars  -> 400 "String should have at most 6000 characters"
  keyterms_prompt > 100    -> 400 "keyterms_prompt exceeds 100 terms (got 101)"

=== Secondary finding: misleading error on overstated WAV data-chunk size ===
A complete, valid WAV header whose data-chunk size field is overstated returns:
  400 "stream ended before a complete WAV header arrived"
The header is in fact complete; only the data size field is wrong. Misleading message.
